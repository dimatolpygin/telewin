## Что за проект

Клиент telewin — сеть хозяйственных магазинов «Домашний мастер» (masterberez.ru), две точки: Микрор-н и п.ш. Берёзовская. Товароучёт в десктопной «Мемо Фора» (memo4x4.ru).

**Веха 1 (текущая)**: чат-боты **VK и MAX**, которые отвечают покупателям о наличии и цене товара по прайсу из «Мемо Фора». Дальше: обмен между магазинами (веха 2), прогноз закупок (веха 3).

> Не путать: **вехи** — это крупные куски проекта (1 боты / 2 обмен / 3 прогноз).
> **Этапы 0–10** — это разбивка разработки вехи 1 в `docs/ROADMAP.md`. Слово «этап» везде
> означает этап разработки 0–10.

Архитектура — три звена: Фора выгружает прайс командой → по FTP летит на наш сервер → бот (Node.js, polling) читает и отвечает. Наличие/цена строго из прайса, ИИ только нормализует запрос.

## Главный принцип — «не врать»

Цена и остаток — только детерминированным запросом к БД. ИИ не генерирует числа: нормализует запрос и обрамляет найденный факт. Не нашли — честно «не нашёл» + похожее из базы. В ответе всегда дата актуальности. На FTP реально прилетали пустышки 50 КБ вместо 2.4 МБ — загрузчик обязан валидировать файл до загрузки.

## Архитектурные заметки (всплыли в переписке, влияют на решения)

- **Источник прайса обязан быть сменяемым.** Клиент прямо просил: «нужна будет возможность менять адрес сервера», и рассматривает свой FTP. Приём файла он может забрать себе целиком («как она туда попадёт, это уже будет моя задача»). Значит адрес, логин, папка и протокол — в `.env`, не в коде. Источник абстрагируем: наш FTP / его FTP / локальная папка — для бота это один интерфейс «дай свежий прайс».

- **Свежесть данных — реальный риск, а не теория.** Автозапуск клиент забрал себе, выгрузка сейчас ручная (клик по ярлыку), а сам он «не так часто оказывается у своего сервера» и загружен. Прайс легко окажется вчерашним. Бот обязан показывать дату актуальности и считать её **по каждому магазину отдельно**; выдавать старое за свежее нельзя.

- **Остатки по отделам не суммировать самим.** В данных есть расхождения: «Болт M 5*12» — общий 424 при 158+265=423. Колонки берём как есть из файла.

- **Штрихкод — ключ слияния магазинов, но в боевом формате его НЕТ.** Если клиент разнесёт магазины на разные серверы (он это сейчас решает), два файла придётся сливать по артикулу, а он внутренний код Форы и между независимыми базами может разъехаться. Отсюда просьба вернуть штрихкод в выгрузку **до** разнесения баз.

- **Смена формата меняет и состав строк.** 11-колоночный образец — 8 389 позиций, боевой 8-колоночный — 11 888. Не предполагать, что наборы строк совпадают между форматами.

- **Масштаб — ~12 тыс позиций.** Для Postgres и pgvector это мизер, на поиске экономить не нужно.

- **Оба магазина уже в одном файле** (отдельные колонки Микрор-н и п.ш. Березовская). Пока база одна — слияние не нужно вообще, бот сразу отвечает по каждой точке.

- **MAX**: токен передавать только заголовком `Authorization`, query-параметр `?access_token=` устарел и отдаёт `verify.token`.

- **Манера общения ИИ** — референс `C:\Users\GigaChat\Downloads\vk0043` (Python-демо): живой человек, а не «тупой ИИ-бот».

## Как работаем

**Переписка с клиентом ведётся по навыку `ok_otvet`, метод 70/30.** На каждый ответ клиента выдаём ДВЕ части:
1. Комментарий для пользователя (Димы) — разбор: что происходит, где риск, тактика хода.
2. Готовый текст для клиента — копипастом, без тире, эмодзи и markdown, простым языком.

Работаем по одному сообщению за ход: пользователь пересылает ответ клиента — готовим следующее. Не забегать вперёд. Проверять каждый этап фактами (не верить «на слово», что что-то заработало).

## Быстрая проверка FTP (пришёл ли свежий прайс)

```bash
curl -s "ftp://ЛОГИН:ПАРОЛЬ@87.58.210.46:21/price/" --ftp-pasv
```
Логин и пароль — в `доступы.txt` / `docs/ACCESSES.md`. Показывает файлы в папке приёма.

Сервер в UTC, клиент в UTC+7: **время сервера + 7 = время клиента**. В имени файла Фора пишет местное время клиента, в mtime — UTC.

Ориентир: боевой прайс весит ~2.4 МБ. **Файл ~50 КБ — это пустышка**, признак того, что Фора не достучалась до данных.
