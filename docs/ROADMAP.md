# Дорожная карта реализации

11 этапов (0–10) от пустого репозитория до бота в бою. Каждый этап заканчивается
**демонстрируемым результатом** — тем, что можно потрогать руками.

Ключевая идея: **MVP-first**. Ядро проекта — работа с прайсом, поэтому этапы 1–5 детально
про данные: распарсить, проверить, не соврать, найти. ИИ и каналы наслаиваются сверху
и не требуют перепиливания базы.

**Главный принцип всего проекта — «не врать».** Цена и остаток берутся только
детерминированным запросом к БД. ИИ не генерирует числа: он нормализует запрос покупателя
и обрамляет уже найденный факт. Ответ всегда содержит дату актуальности данных.

> **Где смотреть прогресс**: текущий статус — в [`STATUS.md`](STATUS.md).
> Закрытие этапа сопровождается git-тегом `stage-N-done`.
> Правило: **за один заход выполняется один этап**, человек проверяет каждый.

| # | Этап | Главный артефакт | Зависит от |
|---|---|---|---|
| 0 | Каркас и Docker-стек | `docker compose up` поднимает app+pg+redis, `/health` отвечает | — |
| 1 | Парсер прайса + CLI | CLI печатает разбор обоих образцов с автоопределением раскладки | 0 |
| 2 | Схема БД и импорт с валидацией | Пустышка 50 КБ отбита, боевой файл загружен атомарно | 1 |
| 3 | Забор с FTP (источник в конфиге) | Свежий файл сам приезжает с FTP и импортируется | 2 |
| 4 | Детерминированный поиск | CLI отдаёт цену и остатки по точкам, цифры сходятся с SQL | 2 |
| 5 | Семантика и гибридный ранкинг | «гвозди сотка» находит «Гвоздь строительный 100» | 4 |
| 6 | ИИ-слой + Telegram-обкатка | Живой бот отвечает по реальной базе с датой актуальности | 5 |
| 7 | Антивраньё: тест-набор | Прогон N вопросов, числа сверены с БД, отчёт | 6 |
| 8 | Мультимагазин / мультиисточник | Два файла с разных точек, у каждой своя свежесть | 4 |
| 9 | Деплой на чистый сервер + CI/CD | Push в master → бот живёт 24/7 | 6 |
| 10 | Каналы VK и MAX | Покупатель пишет в VK и MAX, получает ответ | 9 |

## Этап 0 — Каркас и Docker-стек

**Цель**: пустой, но рабочий проект, в котором есть всё для следующих этапов.

**Что делаем**:
- Node.js LTS + TypeScript, Fastify, pino (логи на русском, `pino-pretty`).
- `docker-compose`: app + Postgres 16 + Redis. На сервере ничего нет — ставим с нуля.
- Drizzle ORM + drizzle-kit, автоприменение миграций в entrypoint контейнера перед стартом app.
- `tsx watch` + volume mount для авто-пересборки.
- **Безопасность с первого коммита**: `.env` в `.gitignore`, `.env.example` с пустыми плейсхолдерами.
  Репозиторий публичный — ни одного секрета в коде и истории.

**Критерии приёмки** (закрытие → tag `stage-0-done`):
- [x] `docker compose up` поднимает три контейнера, все healthy
- [x] `GET /health` отвечает 200 и пишет в лог строку на русском с датой и временем
- [x] Миграции применяются автоматически при старте контейнера, повторный старт не ломается
- [x] Правка файла в `src/` перезапускает app без пересборки образа
- [x] `git log -p` не содержит ни одного секрета; `.env` в `.gitignore` с первого коммита
- [x] `.env.example` перечисляет все переменные с пустыми значениями

**Заметки этапа**:
- На Windows и macOS inotify не проходит через bind mount — `tsx watch` не видел правок.
  Лечится опросом файлов: `CHOKIDAR_USEPOLLING=true` (задано в `docker-compose.yml`,
  переопределяется через `.env`). На Linux-сервере можно выключить.
- `drizzle-orm` поднят до `^0.45.2`: в версиях ниже — SQL-инъекция через неэкранированные
  идентификаторы (GHSA-gpj5-g38j-94v9). Для поиска по вводу покупателя это критично.
- В `npm audit` остаются 4 moderate: esbuild dev-server, транзитивно через `drizzle-kit`.
  Штатный «фикс» откатывает drizzle-kit до 0.18.1 — хуже. Это devDependency, dev-сервер
  esbuild мы не поднимаем. Оставлено осознанно.

## Этап 1 — Парсер прайса + CLI

**Цель**: научиться читать любой присланный прайс и доказать это на обоих реальных образцах.

**Что делаем**:
- Чтение `.xls` (BIFF, старый Excel, cp1251) и `.xlsx`.
- **Автоопределение раскладки колонок** — формат НЕ фиксирован, клиент его меняет:
  - 11 колонок: штрихкод, артикул, наименование, ед.изм, производитель, цена, остаток общий, Микрор-н, п.ш.Березовская, категория, вид товара;
  - 8 колонок (боевой): те же, но БЕЗ штрихкода, категории и вида товара.
  - Определять по числу колонок и типам ячеек, не по жёсткому порядку.
- Цена: десятичный разделитель — запятая (`3,5` → `3.5`).
- Заголовков нет, данные с первой строки.
- **Остатки по отделам не суммируем сами** — берём колонки как есть (в данных есть расхождения:
  на «Болт M 5*12» общий 424 против 158+265=423).
- CLI: `price:parse <файл>` — печатает раскладку, число строк, примеры позиций, статистику.

**Критерии приёмки** (закрытие → tag `stage-1-done`):
- [x] `price:parse samples/boevoy_прайс_2026-07-08.xls` → раскладка «8 колонок», 11 888 строк
- [x] `price:parse samples/2026-07-06T06-25-47.xlsx` → раскладка «11 колонок», 8 389 строк
- [x] Раскладка определяется автоматически, без флага на входе
- [x] Кириллица в наименованиях читается корректно (не кракозябры)
- [x] Цена `3,5` распарсена как число `3.5`
- [x] Позиция «Болт M 5*12» отдаёт остатки Микрор-н `158` и Березовская `265` раздельно, общий `424` берётся из файла, а не считается
- [x] Битый файл (обрезанный, пустой, не Excel, HTML-страница) не роняет парсер, а даёт внятную ошибку
- [x] Пустышка 50 КБ с FTP разбирается честно (122 позиции) и помечается как неполная выгрузка

> **Критерий про пустышку исправлен по факту (2026-07-16).** Он был написан в предположении,
> что пустышка 50 КБ — битый файл. Это не так: скачали её с FTP и вскрыли — валидный
> Composite Document от той же Форы, правильная 8-колоночная раскладка, 122 настоящих товара
> (выгрузился один отдел, электрика). Ломать в ней нечего, и парсер, объявляющий её битой,
> врал бы. Опасна она ровно обратным — правдоподобностью: загрузи её бот, и он честно скажет
> «нет в наличии» про 11 766 товаров. Это не задача парсера, а задача валидатора импорта
> (этап 2): у него есть с чем сравнивать — прошлый успешный импорт. Парсер отдаёт факты
> и вешает предупреждение, решение о блокировке принимается этапом 2.

## Этап 2 — Схема БД и импорт с валидацией

**Цель**: сердце «не врать». Мусор не должен попадать в базу, а хорошие данные — подменяться частично.

**Что делаем**:
- Схема (Drizzle): `shops`, `imports`, `items`, `stock`.
- **Канонический вид**: `stock` в длинном формате — строка на каждую пару (магазин, товар).
  Файл с двумя колонками магазинов даёт две строки. Так раскладка файла перестаёт волновать бота
  и заранее готова к двум файлам с разных точек (этап 8).
- **Валидация ДО загрузки** (урок с боевого FTP — там реально лежат четыре пустышки по 50 КБ
  вместо 2.4 МБ; загрузи их бот — и он честно скажет покупателям «ничего нет в наличии»):
  - минимальный порог строк;
  - сравнение с прошлым успешным импортом (отбивать, если строк стало меньше половины);
  - структура распарсилась.

  > **Проверено на этапе 1: «структура распарсилась» пустышку НЕ ловит.** Скачали её с FTP —
  > это валидный .xls с правильной раскладкой и 122 настоящими товарами. Парсер разбирает её
  > без единой ошибки. Значит единственная защита здесь — **порог строк и сравнение с прошлым
  > импортом** (122 против 11 888 — это 1%). Не рассчитывать, что пустышка отвалится сама
  > где-то в чтении файла: она не отвалится.
- **Атомарность**: грузим в новый `import_id` → валидируем → только потом переключаем указатель «текущий».
- **Дедуп по хешу файла** — один и тот же файл не грузим дважды.
- Свежесть фиксируется по каждому магазину отдельно.
- CLI: `price:import <файл>`, `price:imports` (список импортов со статусами).

**Критерии приёмки** (закрытие → tag `stage-2-done`):
- [ ] `price:import samples/boevoy_прайс_2026-07-08.xls` → импорт со статусом `ok`, в `stock` 11 888×2 строк (по строке на магазин)
- [ ] Повторный импорт того же файла отбивается как дубль по хешу, новый импорт не создаётся
- [ ] Импорт пустышки 50 КБ **отбит** с внятной причиной в логе, указатель «текущий» НЕ сдвинулся
- [ ] После отбитого импорта `price:find` продолжает отдавать данные прошлого хорошего импорта
- [ ] У каждого магазина своя дата последней успешной загрузки, видна в `price:imports`
- [ ] Прерывание импорта на середине не оставляет частичных данных в «текущем»

## Этап 3 — Забор прайса с FTP (источник в конфиге)

**Цель**: файл сам приезжает и попадает в базу. Клиент хочет менять адрес сервера — значит адрес в конфиге.

**Что делаем**:
- FTP-клиент: опрос папки, скачивание новых файлов, передача в импортёр этапа 2.
- **Источник целиком в конфиге** (`.env`): протокол, хост, порт, логин, пароль, папка.
  Клиент просил возможность сменить адрес — это должна быть правка конфига, не кода.
- Абстракция источника: FTP или локальная папка. Клиент может унести приём файла себе —
  бот не должен от этого разваливаться.
- Авто-очистка старых файлов, чтобы папка не пухла.
- Дебаунс: файл дочитывается только когда докачался (мы видели, как 2.4 МБ льётся ~5 минут).

**Критерии приёмки** (закрытие → tag `stage-3-done`):
- [ ] Кладём новый файл на реальный FTP `87.58.210.46:/srv/foraprice/price/` → он сам скачивается и импортируется
- [ ] Лог по-русски показывает: файл найден, скачан, размер, валидация, импорт
- [ ] Смена адреса источника в `.env` → бот берёт прайс с другого адреса без правки кода
- [ ] Переключение источника на локальную папку работает так же
- [ ] Файл в процессе заливки не импортируется недокачанным
- [ ] Уже обработанные файлы повторно не скачиваются

## Этап 4 — Детерминированный поиск

**Цель**: витрина правды. Числа берутся из БД и сходятся с прямым SQL. Никакого ИИ на этом этапе.

**Что делаем**:
- Точное совпадение по артикулу и штрихкоду (если он есть в формате).
- Полнотекстовый поиск (Postgres FTS, конфигурация `russian`).
- `pg_trgm` — устойчивость к опечаткам.
- Единая функция поиска отдаёт: наименование, цена, остаток по каждому магазину, дата актуальности по каждому магазину.
- CLI: `price:find "<запрос>"` — таблица результатов.

**Критерии приёмки** (закрытие → tag `stage-4-done`):
- [ ] `price:find "00008"` находит «Болт M 5*12» точным совпадением по артикулу
- [ ] `price:find "болт м5"` находит позицию полнотекстом
- [ ] Опечатка (`болd м5`) всё равно находит позицию через триграммы
- [ ] Вывод содержит цену, остаток Микрор-н, остаток Березовская и дату данных по каждой точке
- [ ] Цифры в выводе совпадают с прямым SQL-запросом к таблице
- [ ] Запрос-пустышка («асдфгх») честно отдаёт «не найдено», а не случайную позицию
- [ ] Поиск по 12 тыс позиций укладывается в разумное время (< 300 мс)

## Этап 5 — Семантика и гибридный ранкинг

**Цель**: покупатель говорит по-человечески, а не артикулами.

**Что делаем**:
- Эмбеддинги позиций + pgvector (12 тыс строк — мизер для pgvector).
- Гибридный ранкинг: точное совпадение → FTS → триграммы → вектор, со взвешиванием.
- **Открытый вопрос этапа**: чем считать эмбеддинги. OpenRouter — это в первую очередь чат-модели,
  эмбеддинги там может не быть. Варианты: отдельный провайдер или локальная модель.
  Решение принимается в начале этапа и записывается в `DECISIONS`.
- Запасной путь: если семантика окажется избыточной, связка «нормализация запроса ИИ + FTS + триграммы»
  на 12 тыс позиций может закрыть задачу сама.

**Критерии приёмки** (закрытие → tag `stage-5-done`):
- [ ] `price:find "гвозди сотка"` находит «Гвоздь строительный 100» без ручного словаря синонимов
- [ ] Точное совпадение по артикулу всегда стоит выше семантического
- [ ] Широкий запрос («крепёж») отдаёт список кандидатов, а не одну случайную позицию
- [ ] Решение по источнику эмбеддингов зафиксировано в документации
- [ ] Ранкинг воспроизводим: один и тот же запрос даёт один и тот же порядок

## Этап 6 — ИИ-слой + Telegram-обкатка

**Цель**: первая живая вертикаль, которую можно показать клиенту.

**Что делаем**:
- grammY, обкаточный бот `@NikaAi1Bot` (Telegram — временный канал на время разработки).
- OpenRouter, `anthropic/claude-haiku-4.5`, temperature ~0.8, **function calling**.
- **Жёсткое правило**: ИИ вызывает инструмент `search_price(query)`, получает строки из БД
  и формулирует ответ **только по ним**. Числа ИИ не выдумывает. Факт (наименование, цена,
  остаток по точкам) собирает код, ИИ обрамляет.
- Не нашли — честное «не нашёл» плюс похожее **из базы**.
- Несколько совпадений — список и уточняющий вопрос, а не выбор наугад.
- В ответе всегда дата актуальности данных.
- Манера общения — живая, не «тупой ИИ-бот». Референс: `C:\Users\GigaChat\Downloads\vk0043`.
- Логи pino: каждое входящее/исходящее, каждый tool-call с аргументами и результатом,
  каждый вызов ИИ (модель, латентность, токены), request-id сквозь весь путь.

**Критерии приёмки** (закрытие → tag `stage-6-done`):
- [ ] Пишем боту в Telegram «есть болт м5 на 12?» → отвечает реальной ценой и остатками по двум точкам
- [ ] В ответе есть дата актуальности данных
- [ ] Числа в ответе бота совпадают с `price:find` и с прямым SQL
- [ ] Запрос про несуществующий товар → честное «не нашёл» + похожее из базы, без выдумок
- [ ] Широкий запрос («есть саморезы?») → уточняющий вопрос со списком, а не случайная позиция
- [ ] В логах видно: входящее сообщение, tool-call с аргументами, результат из БД, ответ ИИ
- [ ] Название магазинов в ответе — в том виде, как просил клиент

## Этап 7 — Антивраньё: тест-набор и прогон

**Цель**: доказать, что бот не врёт, — не на ощущениях, а прогоном.

**Что делаем**:
- CLI-гонялка ИИ по прайсам без Telegram: `ai:ask "<вопрос>"` — полный путь запроса в консоли.
- Батч-прогон: набор из N реальных вопросов покупателя → ответы → **автосверка чисел с БД**.
- Отчёт: где сошлось, где ИИ подставил число не из базы, где выдумал товар.
- Набор пополняется по мере находок и служит регрессией на будущее.

**Критерии приёмки** (закрытие → tag `stage-7-done`):
- [ ] `ai:ask "есть болт м5"` отрабатывает полный путь и печатает найденное + ответ ИИ
- [ ] Батч-прогон по набору вопросов даёт отчёт с процентом совпадения чисел с БД
- [ ] Любое число в ответе ИИ прослеживается до конкретной строки БД
- [ ] Вопрос про заведомо несуществующий товар не порождает выдуманную позицию
- [ ] Набор вопросов лежит в репозитории и прогоняется одной командой

## Этап 8 — Мультимагазин / мультиисточник

**Цель**: пережить сценарий, когда клиент разнесёт магазины на разные серверы.

**Что делаем**:
- Два файла, по одному с точки, слияние в общий каталог.
- **Ключ слияния**: штрихкод надёжнее (заводской, совпадает между базами), но в боевом
  8-колоночном формате его НЕТ — остаётся артикул, а он внутренний и между базами может разъехаться.
  Отсюда задача: просить клиента вернуть штрихкод в формат выгрузки **до** разнесения баз.
- Свежесть по каждому магазину отдельно: если Микрор-н обновился сегодня, а Березовская три дня назад —
  бот обязан показать это раздельно, а не подать оба как актуальные.

**Критерии приёмки** (закрытие → tag `stage-8-done`):
- [ ] Подкладываем два файла (по одному на магазин) → бот отвечает по обеим точкам
- [ ] Позиция, встречающаяся в обоих файлах, склеивается в одну, а не двоится
- [ ] Разная свежесть точек видна покупателю в ответе раздельно
- [ ] Сценарий «один файл с двумя колонками» продолжает работать как раньше
- [ ] Слияние по штрихкоду работает, когда штрихкод есть; фолбэк на артикул — когда нет

## Этап 9 — Деплой на чистый сервер + CI/CD
