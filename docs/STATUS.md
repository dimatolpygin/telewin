**2026-07-16 — Этап 3: Забор прайса с FTP — tag `stage-3-done` — коммит `83eb549`**

Проверено человеком: три шага прогнаны в cmd.exe, вывод совпал с ожидаемым.

Что сделано: `src/price/источник.ts` (абстракция FTP / локальная папка, конфиг из `.env`),
`src/price/забор.ts` (один проход забора), `src/price/свежесть.ts` (время выгрузки из имени
файла, показ в поясе клиента UTC+7), CLI `price:fetch`. Импортёр принял `ОпцииИмпорта`
{файлОт, исходноеИмя}; `price:imports` показывает даты в поясе клиента. Поставлен `basic-ftp`.

Чем подтверждено (человеком в cmd.exe + мной вживую на боевом FTP):
- `price:fetch` забрал реальный свежий файл `2026-07-16T13-57-35.xls` с FTP `87.58.210.46`,
  импортировал (#1, 11 867 позиций) — файл сам приехал и попал в базу.
- «Данные от 13:57» совпало со временем в ИМЕНИ файла, а не со временем скачивания.
- Повторный забор не качал: `уже обрабатывали — не скачиваю`, `новых файлов нет`.
- Дебаунс: растущий файл отбит как «ещё заливается», код 3 (проверял я локально).
- Смена источника на локальную папку — тем же кодом, только `PRICE_SOURCE`.

Нетривиальные решения:
- **Свежесть — из ИМЕНИ файла, а не из FTP-mtime.** basic-ftp на нашем vsftpd вернул mtime
  пустым (нет MLSD). Имя файла Форы (`…T13-57-35`) точнее и всегда есть. Порядок доверия:
  имя → mtime источника → локальный mtime.
- **Время клиента UTC+7** (`Asia/Novokuznetsk`): имя записано в местном времени клиента, храним
  момент в UTC, показываем покупателю в UTC+7. Проверено: `15-56-31` → хранится `08:56Z` → `15:56`.
- **Авто-очистка источника по умолчанию выключена** (`PRICE_KEEP_FILES=0`): иначе при источнике
  `local=./samples` удалила бы боевые образцы. На сервере включить.
- **`price:fetch` — один проход, не демон.** Периодический опрос — задача деплоя этапа 9.
- **FTP-пароль в `.env`** (в `.gitignore`), в коде и `.env.example` пусто.

**2026-07-16 — Этап 1: Парсер прайса + CLI — tag `stage-1-done` — коммит `1e9ef4c`**

Проверено человеком: все команды прогнаны в cmd.exe, числа сверены.

Что сделано: `src/price/раскладка.ts` (роли колонок, автоопределение по ширине строки и типам
ячеек), `src/price/парсер.ts` (чтение `.xls` BIFF/cp1251 и `.xlsx`), `src/price/ошибки.ts`,
CLI `src/cli/price-parse.ts` с флагом `--найти`.

Чем подтверждено:
- Боевой `.xls` → раскладка «8 колонок», 11 888 позиций, пропущено 0, совпадение 100%.
- `.xlsx` → раскладка «11 колонок», 8 389 позиций, пропущено 0. Флагов на входе нет,
  раскладка определяется сама.
- «Болт M 5*12» → цена `3.5` (в файле `3,5`), общий `424`, Микрор-н `158`, Березовская `265`.
  Сумма отделов дала бы 423 — берётся 424 из файла.
- Пустышка 50 КБ → 122 позиции + предупреждение о неполной выгрузке, без ошибки.
- Несуществующий файл → `ERROR … Файл не найден`, ненулевой код выхода.
- Кириллица читается и в отчёте, и в логах.

Нетривиальные решения:
- **Критерий про пустышку был неверен и исправлен по факту.** Считалось, что пустышка 50 КБ —
  битый файл, и парсер должен «дать внятную ошибку». Скачали её с FTP и вскрыли: валидный
  Composite Document от той же Форы, правильная 8-колоночная раскладка, 122 настоящих товара
  (выгрузился один отдел, электрика). Ломать нечего — парсер, объявляющий её битой, врал бы.
  Опасна она правдоподобностью: загрузи её бот, и он честно скажет «нет в наличии» про 11 766
  товаров. Ловить обязан валидатор импорта на этапе 2, больше нечем.
- **Расхождение «общий ≠ сумма отделов» массовое**: 572 позиции из 11 888 и 630 из 8 389.
  Правило «не суммировать самим» подтверждено замером, а не догадкой. Остатки бывают дробными
  (метры, килограммы), артикул бывает пустым — записано в `DATA_прайс.md`.
- **SheetJS молча парсит мусор**: текстовый файл и HTML-страницу с ошибкой он читает как
  таблицу из одной ячейки, не бросая исключения. Поэтому защита от чужого файла — определение
  раскладки, а не try/catch. Обрезанный файл валит его невнятным `Cannot set properties of
  undefined` — переведено на русский с подсказкой про размер.
- **`xlsx` поставлен с CDN SheetJS (`0.20.3`), не с npm**: в npm-реестре пакет заброшен на
  `0.18.5` с prototype pollution (CVE-2023-30533) и ReDoS (CVE-2024-22363), а через парсер
  проходит файл из внешнего источника. Версия и хеш зафиксированы в `package-lock.json`.
  **Следствие для этапа 9: сборке нужен доступ к `cdn.sheetjs.com`** (проверено, `npm ci`
  в Docker проходит).
- **Кириллица в логах на Windows**: pino через `transport` уходит в worker-поток и пишет сырые
  UTF-8 байты в дескриптор 1 (sonic-boom), минуя консоль; cmd.exe в CP866 читает их как 866 и
  выдаёт «╨а╨░╨╖». Поэтому pino-pretty подключён потоком с явным `process.stdout` (он идёт через
  `WriteConsoleW`). `chcp 65001` не нужен. Побочно выправился порядок строк — асинхронный воркер
  печатал лог с задержкой.
- **`logger.ts` отвязан от `config.ts`**: логгер требовал пароль от Postgres, чтобы напечатать
  строку, из-за чего CLI не запускался без базы. `LOG_LEVEL` читается из env напрямую.

## Протокол обновления

**При старте сессии**:
1. Прочитать этот файл.
2. `git tag -l "stage-*"` и сверить с колонкой «Закрывающий тег». Тег без записи в таблице = таблица устарела, обновить.
3. `git log --oneline -10` — что менялось последним.
4. Только после этого приступать к работе.

**При взятии этапа в работу**:
1. Обновить «Текущий этап» и «Активная работа».
2. Статус 🚧 в таблице.
3. Закоммитить отдельно: `chore(status): start stage N`.

**При закрытии этапа**:
1. Убедиться, что все чекбоксы в `ROADMAP.md` отмечены `[x]` и реально проверены человеком.
2. Создать тег: `git tag stage-N-done -m "<описание>"`.
3. В таблице: ✅, «Закрывающий тег», «Последний коммит» (`git rev-parse --short HEAD`), «Дата закрытия».
4. Добавить запись в «Историю закрытий».
5. Указать новый «Текущий этап» и «Следующий шаг».
6. Закоммитить: `chore(status): close stage N`.

**Если этап заблокирован**:
1. Статус ⏸ в таблице.
2. В «Известные блокеры»: что блокирует, кого ждём, что нужно для разблокировки.
