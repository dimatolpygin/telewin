**Этап**: 5 — Семантика и гибридный ранкинг. В работе.

**Решение по эмбеддингам (закрыт открытый вопрос)**: OpenRouter API (у него теперь есть
`POST /api/v1/embeddings` — прежняя запись в CLAUDE.md, что «эмбеддингов может не быть»,
устарела), модель `qwen/qwen3-embedding-4b`, 2560 мерностей. Выбрана замером на боевом запросе
«гвозди сотка»: из восьми моделей (bge-m3, multilingual-e5, text-embedding-3-small/large,
gemini, qwen3-4b/8b) только qwen3 ставит настоящие гвозди выше «жидких гвоздей» (клея). Тот же
ключ OpenRouter, что для чата этапа 6 — новой инфраструктуры и провайдера не добавляем. Подробно
в `docs/PROJECT.md` (ADR).

**Сводка задач**: покупатель говорит по-человечески («гвозди сотка»), а не артикулами. Поверх
детерминированного поиска (этап 4) — эмбеддинги позиций (pgvector) и гибридный ранкинг. Точное
по артикулу/штрихкоду короткозамыкает (всегда выше семантики). Индекс эмбеддингов — точный скан
(без ivfflat/hnsw): 2560 мерностей превышают лимит ANN-индексов 2000, а на 12k строк точный
поиск и так ~15 мс, зато ранкинг строго воспроизводим.

**Отправная точка**: `src/price/поиск.ts` → `искать()` (этап 4). Три канала (артикул/штрихкод →
FTS `russian` → триграммы) уже дают отранжированный список; этап 5 добавляет четвёртый —
семантический — и общий взвешенный ранкинг. Нормализация запроса — функция `norm_search` (0002).

**2026-07-16 — Этап 4: Детерминированный поиск — tag `stage-4-done` — коммит `c1e4817`**

Проверено человеком: четыре команды `price:find` прогнаны в cmd.exe, вывод совпал с ожидаемым
до цифры.

Что сделано: `src/price/поиск.ts` → `искать()` (три канала: точное по артикулу/штрихкоду →
FTS `russian` → триграммы `pg_trgm`), миграция `0002` (функция `norm_search`, GENERATED-столбец
`наименование_norm`, GIN-индексы FTS и trgm, btree артикул/штрихкод). CLI `price:find`
переписан под item-centric вывод (цена одна, остаток и свежесть по каждой точке). Прежний
`найтиВТекущем` (ilike-подстрока) удалён.

Чем подтверждено (человеком в cmd.exe + мной в SQL):
- `price:find "00008"` → ровно «Болт M 5*12», метка «точно по артикулу»; цена 3.50, Микрор-н 128,
  Березовская 265, общий по сети 394 (не сумма — 128+265=393 — берётся из файла), дата по точкам.
- `price:find "болт м5"` → «Болт M 5*12» первым, метка «по названию» (FTS).
- `price:find "болd м5"` (опечатка, латинская d) → «Болт M 5*12» первым, метка «похоже» (триграммы).
- `price:find "асдфгх"` → «ничего не нашлось».
- Цифры совпали с прямым SQL (join items+stock+shop_state): 3.50 · 128 · 265.
- Стемминг: «болты» (мн.ч.) находит 350 позиций «Болт» по FTS.
- Чистое время SQL — ~14 мс (EXPLAIN ANALYZE), в CLI 37–55 мс с холодным стартом tsx (< 300 мс).

Нетривиальные решения:
- **Направление нормализации — критично, поймано на боевых данных.** `norm_search` сводит
  латинские гомоглифы в кириллицу (m→м, c→с…), а не наоборот. Обратный свод (кириллица→латиница)
  ломал русский FTS-стемминг: «саморезы» переставали находить «саморез», т.к. смешанный алфавит
  (`camopeз`) не распознаётся словарём `russian`. Свод в кириллицу оставляет русские слова
  кириллицей (стеммятся), а латинскую `M` из «Болт M 5*12» приводит к `м` — так «болт м5»
  (кириллица, слитно) совпадает по FTS. Критерий про FTS был написан на предположении, что
  «болт м5» совпадёт напрямую; без нормализации не совпадал (токен `м5` ≠ `m`+`5`).
- **Нормализация — одной функцией** `norm_search`, общей для GENERATED-столбца и запроса:
  один алгоритм на обе стороны, иначе строка в базе и запрос разъедутся. Разбивает букву/цифру
  пробелом («м5»→«м 5»), lower, свод гомоглифов. IMMUTABLE (иначе нельзя звать в GENERATED).
- **Точное совпадение по артикулу/штрихкоду короткозамыкает**: найден артикул → отдаём только его.
- **JIT отключён** на поиске (`SET LOCAL jit = off`): экономит ~0.1 с компиляции на мелком запросе.
- **Запрос от `shop_state`** (текущий снимок каждого магазина), не от «последнего импорта» —
  отбитый импорт не может просочиться. Свежесть берётся по каждой точке отдельно (готово к этапу 8).

Нетривиальные решения:
- **Критерий про пустышку был неверен и исправлен по факту.** Считалось, что пустышка 50 КБ —
  битый файл, и парсер должен «дать внятную ошибку». Скачали её с FTP и вскрыли: валидный
  Composite Document от той же Форы, правильная 8-колоночная раскладка, 122 настоящих товара
  (выгрузился один отдел, электрика). Ломать нечего — парсер, объявляющий её битой, врал бы.
  Опасна она правдоподобностью: загрузи её бот, и он честно скажет «нет в наличии» про 11 766
  товаров. Ловить обязан валидатор импорта на этапе 2, больше нечем.
- **Расхождение «общий ≠ сумма отделов» массовое**: 572 позиции из 11 888 и 630 из 8 389.
  Правило «не суммировать самим» подтверждено замером, а не догадкой. Остатки бывают дробными
  (метры, килограммы), артикул бывает пустым — записано в `DATA_прайс.md`.
- **SheetJS молча парсит мусор**: текстовый файл и HTML-страницу с ошибкой он читает как
  таблицу из одной ячейки, не бросая исключения. Поэтому защита от чужого файла — определение
  раскладки, а не try/catch. Обрезанный файл валит его невнятным `Cannot set properties of
  undefined` — переведено на русский с подсказкой про размер.
- **`xlsx` поставлен с CDN SheetJS (`0.20.3`), не с npm**: в npm-реестре пакет заброшен на
  `0.18.5` с prototype pollution (CVE-2023-30533) и ReDoS (CVE-2024-22363), а через парсер
  проходит файл из внешнего источника. Версия и хеш зафиксированы в `package-lock.json`.
  **Следствие для этапа 9: сборке нужен доступ к `cdn.sheetjs.com`** (проверено, `npm ci`
  в Docker проходит).
- **Кириллица в логах на Windows**: pino через `transport` уходит в worker-поток и пишет сырые
  UTF-8 байты в дескриптор 1 (sonic-boom), минуя консоль; cmd.exe в CP866 читает их как 866 и
  выдаёт «╨а╨░╨╖». Поэтому pino-pretty подключён потоком с явным `process.stdout` (он идёт через
  `WriteConsoleW`). `chcp 65001` не нужен. Побочно выправился порядок строк — асинхронный воркер
  печатал лог с задержкой.
- **`logger.ts` отвязан от `config.ts`**: логгер требовал пароль от Postgres, чтобы напечатать
  строку, из-за чего CLI не запускался без базы. `LOG_LEVEL` читается из env напрямую.

## Протокол обновления

**При старте сессии**:
1. Прочитать этот файл.
2. `git tag -l "stage-*"` и сверить с колонкой «Закрывающий тег». Тег без записи в таблице = таблица устарела, обновить.
3. `git log --oneline -10` — что менялось последним.
4. Только после этого приступать к работе.

**При взятии этапа в работу**:
1. Обновить «Текущий этап» и «Активная работа».
2. Статус 🚧 в таблице.
3. Закоммитить отдельно: `chore(status): start stage N`.

**При закрытии этапа**:
1. Убедиться, что все чекбоксы в `ROADMAP.md` отмечены `[x]` и реально проверены человеком.
2. Создать тег: `git tag stage-N-done -m "<описание>"`.
3. В таблице: ✅, «Закрывающий тег», «Последний коммит» (`git rev-parse --short HEAD`), «Дата закрытия».
4. Добавить запись в «Историю закрытий».
5. Указать новый «Текущий этап» и «Следующий шаг».
6. Закоммитить: `chore(status): close stage N`.

**Если этап заблокирован**:
1. Статус ⏸ в таблице.
2. В «Известные блокеры»: что блокирует, кого ждём, что нужно для разблокировки.
